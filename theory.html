How LSM Trees work

A compact guide to the write path, read path, compaction, and the trade-offs that make log-structured merge trees useful for write-heavy storage.

ON THIS PAGE

01 THE CORE IDEA

Turn random writes into sequential work

An LSM tree is a storage structure that accepts updates in memory and periodically writes sorted, immutable files to disk. Instead of modifying a disk-resident tree in place for every operation, it batches changes and merges them later. The design was introduced as a way to make write-heavy workloads efficient on secondary storage.

The name describes its shape: a small mutable component sits above a sequence of increasingly large, sorted levels. Each level contains SSTables—immutable sorted-string tables whose keys and values can be indexed and filtered.

02 WRITE PATH

WAL → MemTable → SSTable

1 · Write-ahead log

The update is appended to a durable log before the in-memory structure acknowledges it. If the process crashes, the log can be replayed to recover acknowledged writes.

2 · MemTable

The update enters an ordered in-memory table. Keeping recent writes in memory makes point updates cheap and allows many operations to be sorted together.

3 · Flush

When the MemTable reaches its capacity, it is frozen and written as a new immutable L0 SSTable. A checkpoint and Manifest update describe the durable view.

This batching strategy reduces random disk writes, but it creates multiple versions of a key across memory and files. Reads and compaction must therefore reconcile versions using sequence numbers or timestamps.

03 READ PATH

Search recent data first, then narrow the files

A point lookup usually checks the newest data first, then examines SSTables from newer to older levels. The first visible record with the greatest sequence number wins; a tombstone means the key is logically deleted even if older copies remain physically present.

Indexes

An SSTable index maps key ranges or separator keys to blocks, allowing a reader to seek near the requested key instead of scanning the entire file.

Bloom filters

A Bloom filter can quickly say that a key is definitely absent from a table. A positive result is only a possibility, so the table still verifies the key.

Range scans

Sorted runs make inclusive key ranges efficient: each file can seek to the start key and stream records in order while merging results from several sources.

04 COMPACTION

Merge files and retire obsolete versions

Compaction reads overlapping sorted files, merges their records, and writes new output files. The merge keeps the newest version for each key and can discard obsolete records or tombstones once it is safe to do so.

Leveled

Files are organized into levels with size targets and limited overlap within deeper levels. This can reduce read amplification, at the cost of more rewriting during compaction.

Size-tiered

Similarly sized files are grouped and merged into a larger file. It often writes less eagerly, but can retain more overlapping files and increase read or space amplification.

The right strategy depends on workload shape, latency goals, available write bandwidth, and how much space can be used for temporary and obsolete files.

05 TRADE-OFFS

Pay for batching with amplification

MeasureWhat it capturesTypical pressure
Write amplificationHow many physical records are written for each logical update.Compaction rewrites data.
Read amplificationHow many structures a read must check before finding an answer.Many overlapping runs.
Space amplificationHow much retained physical data exists compared with live logical data.Obsolete versions and tombstones.

LSM systems tune these competing costs with level sizes, compaction policy, caching, filters, indexes, and flush thresholds. The simulator’s Run Statistics panel exposes educational record-count estimates for these same ideas.
